# 说人话

把抽象、工程化、AI 味、过度正式或不好理解的内容，改成中文、直接、可执行的人话表达。

## 适用内容

1. 对话解释。
2. 专业文档段落。
3. 分析结论。
4. 外部确认消息。
5. SOP、AGENTS.md、skill 文档。
6. 评审结论和修改建议。

## 改写规则

1. 不改变业务事实、范围、结论和风险等级。
2. 先说结论，再说原因和下一步。
3. 用短句和具体动作。
4. 少用抽象词；必须使用术语时先解释。
5. 使用项目已有术语，不发明新词；保留字段名、状态名、按钮名、页面名、接口名、角色名和已确认口径。
6. 保留事实、推测、待确认、风险、范围外的边界。
7. 不补不存在的数字、案例、日期、负责人、范围和结论；缺关键信息时标为“待补充”或“需确认”。用户明确要求按逻辑举例时，可以给“示例写法”，但不能当成事实写入正式版本。
8. 删除空泛套话，例如“赋能”“提升体验”“保障能力”“闭环建设”等没有对象、动作和结果的表达。
9. 引用、代码块、表格、别人原话和结构化内容不直接改；如有表达问题，只指出问题和建议。

## 表达与术语

本技能只改善表达，以用户提供的内容和已确认上下文为依据。先理清主旨，再调整信息顺序、句子和用词，让读者容易理解；不承担需求分析、事实调查或历史逻辑维护。

沿用上下文中已确认的名称、对象定义和适用语境。术语不清、准备替换名称或改写可能改变含义时，按需参考用户指定或项目已有的术语库、知识库，仅定位相关定义。含义已经清楚时直接改写，不为润色强制查询资料。

遇到资料冲突或缺少定义时，保留原意并标注具体歧义，继续改写不受影响的内容，不自行裁决口径，也不因此发起代码核验。确需新增概念时，标明候选名称和含义，交由相应领域或术语维护流程判断，不以润色名义确立定义。事实核实由相应专业流程处理，不由表达技能重复调查。

说明文字应让读者找到对象、条件、动作和结果，保留必要字段、数值、例外及适用范围。技术过程可以压缩为易读解释，但不删除影响含义的信息，不擅自搬移资料或新建证据文档；已有相关链接保留。完成时对照原文，确认只是表达更清楚，事实与范围没有变化。

## 输出方式

用户只要求“说人话”时，直接给改写版。需要说明时，再补一句“主要改了哪些表达问题”。

用户要求“检查一下”“只指出问题”时，只输出问题和修改建议，不直接改写全文。问题较多时按优先级标注：

1. 必须改：会误导理解、改变范围、隐藏风险，或让执行方无法行动。
2. 建议改：表达抽象、绕、AI 味重，但不影响事实判断。
3. 看场景：正式文档、汇报或对外话术里可能需要保留的表达。

用户要求改文件时，只直接改普通文本文件，例如 Markdown、TXT、SOP 和说明文档。不直接改代码、配置、JSON、YAML、CSV、表格数据、命令、路径、字段名和结构化数据；遇到这些内容，只给建议或保留原样。

不要把正式文档改成闲聊文案；正式文档仍保持可评审、可执行、可验证。

## 完成标准

1. 事实、范围、结论和风险等级没有变化。
2. 项目术语、字段名和已确认口径没有被替换。
3. 没有新增未经确认的信息；示例内容已明确标注为示例。
4. 正式文档仍可评审、可执行、可验证。
